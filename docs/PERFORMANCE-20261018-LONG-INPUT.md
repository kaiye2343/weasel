# 默认皮肤下长串输入延迟（2026-10-18）

## 状态

用户切换到简洁纯色 neutral/light 后报告延迟，并确认输入越长越明显。本轮在隔离算法测试复现长串按键耗时，尚未修复，也尚未定位到 librime 内部具体函数。不能将本报告表述为完成性能优化。

没有操作用户窗口、键鼠或输入法切换，没有重启日常服务，没有修改日常配置或学习数据库。用户服务仍为 PID 14812，资料根仍为迁移后的 `C:\Users\12877\RimeData`。默认皮肤清单没有图片层。

## 方法与边界

- 使用实际安装 0.17.4.94 的 librime 1.13.1，通过官方 API 在全新临时目录创建会话。
- 复制静态词库、模型、Lua 和编译方案；没有复制真实 `.userdb`。共享静态夹运行结束后仍不包含用户数据库。
- 合成输入串为 `woxiangzaizhelishuruyijuchangyidianzhongwen`，按 16／32／64／128 字母长度重复输入，不提交。
- 分别计时 `RimeProcessKey` 与随后一次 `RimeGetContext`。不创建 HWND，不加载或绘制皮肤，不发送真实桌面按键，不连接用户服务。
- 每个案例新建空学习库，顺序执行；原配置另外复测一次，避免将系统缓存预热误算成开关收益。
- 这不是用户真实按键到屏幕的端到端采样，也不是多种真实语料的全面评测。空学习库、重复输入及系统负载限制了可推广性。

短串测试受缓存与输入音节阶段影响较明显，不能只比较一次短串的中位数就声称某开关节省了多少时间。以上开关没有消除长串高位延迟，未应用到日常方案。

## 生效核验与无效尝试

- 去模型案例使用官方配置 API 确认运行时 `grammar/language` 缺失。
- 去额外模糊音案例确认编译方案不再含十二条规则，且运行时主翻译器使用专用 `wanxiang_perf_nofuzzy` 索引。
- 最初两组去模糊音尝试无效：custom 补丁被重新追加，移除用户 custom 文件后又从共享目录回落读取。最终用显式空补丁覆盖共享补丁；原始尝试记录保留，但不纳入上表或 CSV。
- 首次修改 max_homophones 的准备脚本因其他翻译器也有同名参数而主动停止，未采纳；有效版本仅修改顶层主翻译器区块。

## 判断及下一步

当前证据把主要排查范围缩到 Rime 按键处理阶段；仅凭函数边界计时还不能判定具体是原生分词／拼写图、候选搜索还是其他内部阶段。去除 Lua 后长串峰值仍在，也不能把全部耗时归给 Lua。

下一步应针对隔离长串运行做带调用栈的 CPU 采样，定位热点，再在相同输入与候选结果下验证优化。此处没有经过验证的参数快改；不为追求跑分关闭模型、学习、模糊音、注音或整句能力，也不以更换皮肤／渲染 API 代替算法采样。

临时可通过分段选词缩短未提交拼音的长度；这是使用层缓解，未改变程序行为，也不代表问题已修复。
